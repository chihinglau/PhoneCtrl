## 0. 先读这一节：合规与风险（必须评审）

本方案的目标场景是「在抖音 / 快手极速版内自动看视频、**打卡签到**、处理广告、领取金币类奖励」。在动手前必须明确：

| 风险 | 说明 | 影响 |
|---|---|---|
| 服务条款 | 抖音、快手（含极速版）的用户协议通常禁止使用自动化脚本、外挂、第三方工具模拟人工操作 | 账号警告、限流、封禁；情节严重可能涉及法律责任 |
| 奖励机制 | "看视频得金币""打卡领金币"等奖励面向真实用户活跃，自动化领取可能被判定为刷取 | 收益清零、账号封禁 |
| 打卡连续性 | 连续打卡有累计奖励，漏签或异常点击可能导致连续天数中断 | 累计奖励损失，且不可恢复 |
| 广告 | 自动观看/点击广告可能触发平台反作弊 | 同上，且可能涉及广告主侧计费争议 |
| 设备安全 | 长期无人值守运行 ADB 自动化、安装未知脚本 | 隐私与设备安全风险 |

**建议评审时优先回答：**
1. 用途是自用（自己的账号/设备）还是多设备规模化？规模化风险显著更高。
2. 是否接受"账号可能被封"这一结果？
3. 是否只在测试账号/小号上验证？

> 本方案只描述**技术可行路径与工程量**，不提供绕过平台风控、规避检测的具体技巧。是否实施、如何实施由评审决定。

## 1. 目标与范围

利用现有 PhoneCtrl 投屏/控制系统，以**投屏客户端为操作入口**，覆盖两类目标 App：

**A. 抖音 / 抖音极速版**
- **看视频自动化**：自动上滑切换视频、按观看时长推进
- **广告场景处理**：识别广告页/激励视频入口，执行观看或跳过（遵循上节风险）
- **金币任务**：识别金币挂件与奖励页，触发领取并校验结果

**B. 快手极速版（打卡任务）**
- **每日打卡**：进入任务中心 → 定位打卡入口 → 点击打卡 → 按需要看激励视频 → 点击领取 → 校验金币/连续天数
- **幂等保护**：同一自然日只执行一次，避免重复打卡或漏签（见 §4.8）
- **状态可观测**：打卡结果写入 `monitor.events`，可在客户端查看

两者共同要求：**可观测**——在桌面控制台看到进度、日志、状态，可随时停止。

**明确不在本期范围**：模拟真人行为绕过风控、批量账号矩阵、云端托管、变现结算。

| 自动滑屏 | `lib/swipe.dart` + `/api/autoswipe` | 随机间隔上下左右滑屏 |

### 2.2 现成的「抖音金币」原型（孤立，未接入引擎）

`tools/coin_watch.py` 是一个独立 Python 脚本：
- 直接调 adb，截图后用 ROI 灰度差判断金币挂件是否增长
- 增长后连续 N 秒稳定则上滑切下一个视频
- 参数：`--roi --threshold --stable --cooldown --interval --rounds --max-watch --calibrate`
- ROI 默认 `(0.02, 0.10, 0.18, 0.12)`，基于 EBG-AN00 1080×2340 校准
- **问题**：与 Dart 引擎/投屏客户端零复用；只覆盖"看视频"，不覆盖广告与领取；硬编码设备分辨率

### 2.3 关键差距

| 差距 | 说明 |
|---|---|
| 无抖音剧本 | 全项目未出现抖音包名 `com.ss.android.aweme` / 极速版包名，无抖音 task JSON |
| 无快手剧本 | 全项目无快手包名（极速版 `com.kuaishou.nebula` / 主版 `com.smile.gifmaker`），无打卡任务剧本 |
| 无"打卡"专用阶段 | 现有 phase 面向循环任务，缺少"每日一次 + 幂等"的打卡语义（见 §4.8） |
| 无独立文本输入 API | 仅 `/unlock` 内能发数字键码，搜索/输入场景需扩展 |
| 无 cron 定时 | 滑屏是循环，非按时间段调度；打卡需要"每天一次"的幂等调度 |
| coin_watch 与引擎割裂 | 两套 adb 与识别逻辑，维护成本高 |
| 桌面端无"任务"面板 | 任务提交目前只在 Web 控制台 `/index.html` |

## 3. 整体架构

```
┌──────────────────────────────────────────────────────────┐
│  桌面客户端 win_console/app.py（评审后扩展「任务」面板）      │
│  - 抖音看视频 / 快手打卡  - 进度/日志  - 参数校准  - 多设备    │
└───────────────────┬──────────────────────────────────────┘
                    │ HTTP :8858
┌───────────────────▼──────────────────────────────────────┐
│  server.dart（路由层）                                     │
│  新增：/api/task/douyin、/api/task/kuaishou（提交+status）   │
│  复用：/frame/<s>  /api/status  /api/device/<s>/tap|key|stop │
└───────────────────┬──────────────────────────────────────┘
                    │
┌───────────────────▼──────────────────────────────────────┐
│  Scheduler（状态机，按 serial 隔离）                        │
│  看视频: opening→swiping→[ad?]→[videoAd?]→rewarding→verify │
│  打卡:   opening→nav→checkIn→[videoAd?]→claiming→verify     │
│  复用 detector 三策略 + RewardVerifier，复用 automation 重试  │
└───────────────────┬──────────────────────────────────────┘
                    │ adb / hdc（LinkRouter）
┌───────────────────▼──────────────────────────────────────┐
│  手机：抖音 / 快手极速版（包名见 §4.1）                      │
│  投屏画面 ← scrcpy → 桌面客户端格子                          │
└──────────────────────────────────────────────────────────┘
```

**设计原则**：不为抖音/快手另起一套引擎。把 `coin_watch.py` 的状态机逻辑**翻译进** `Scheduler` + `TaskScript`，识别走 `detector.dart`，控制走 `adb.dart`，UI 走现有桌面客户端。两类 App 共用同一套引擎，仅靠**剧本 + 少量 phase 扩展**区分。

## 4. 关键技术实现

### 4.1 抖音包名与入口

| 版本 | 包名（待设备实测确认） | 入口 Activity |
|---|---|---|
| 抖音 | `com.ss.android.ugc.aweme` | 需 `adb shell monkey` 或 `cmd package resolve-activity` 实测 |
| 抖音极速版 | `com.ss.android.ugc.aweme.lite` | 同上 |

> `adb.openApp(package)` 已存在；Activity 名不写死在代码里，由剧本配置 `package` + 系统默认启动，避免版本升级失效。

### 4.2 看视频循环（复用现有 swipe + 静帧）

- 打开 App → 等待首帧稳定（`automation.waitStable()`）
- 按 `loop.swipe` 配置的间隔上滑：`{from:[0.5,0.8], to:[0.5,0.2], ms:250}`
- 每轮用 `screen.capture()` 取帧，交给识别层判断是否进入广告/奖励页
- `coin_watch.py` 的"金币挂件 ROI 差分"可作为**其中一种识别策略**移植：在 `detector.dart` 新增 `DiffRewardDetector`，用已有 `PngImage.crop()/avgRgb()` 的区域均值差替代 PIL

### 4.3 广告识别与处理

复用 `detector.dart` 三种策略，抖音剧本里按需组合：

| 策略 | 适用 | 配置 |
|---|---|---|
| `region` | 广告页有固定颜色/布局特征 | `ad.region` + `ad.mode:"region"` |
| `template` | 有明确按钮图标（如"跳过"） | 预存模板图 + `mad` 阈值 |
| `ocr` | 文案特征（"广告""立即下载""关闭"） | `ad.keywords` + 外部 tesseract |

处理动作在 `Scheduler` 的 `adClicking` phase：按剧本 `ad.action` 执行 `tap`/`keyEvent(BACK)`/等待；**不实现任何规避检测的行为**。

### 4.4 金币领取与校验（复用 RewardVerifier）

- 入口识别：`videoAd.entryRegion` / `entryKeywords`（如"看视频得金币"）
- 观看：进入激励视频 → 等待 `waitClaimMs`
- 领取：`claimRegion` 点击 → `verifyRegion` 截图
- 校验：`RewardVerifier.verify(before, after)` 对比关键词/数值，默认含"金币"
- 失败重试：走 `automation.recover()`（BACK + 重开 App），记录到 `monitor.events`

### 4.5 坐标校准（关键工程量）

现有全部坐标为 **0~1 归一化相对坐标**（`RPoint/Rect`），与分辨率无关，但**不同机型 UI 布局不同**。抖音剧本需按机型校准以下区域：

- 金币挂件 ROI（参考 coin_watch 默认 `(0.02,0.10,0.18,0.12)`）
- 广告"跳过/关闭"区域
- 激励视频入口与"领取"按钮
- 奖励数值显示区

建议提供校准命令：复用 `coin_watch.py --calibrate` 思路，输出归一化坐标供剧本填写。

### 4.6 后端接口扩展（新增，不改已有）

| 方法 | 路径 | 请求体 | 说明 |
|---|---|---|---|
| POST | `/api/task/douyin` | `{serial, config}` | 提交抖音剧本，复用 `scheduler.submit(TaskScript)` |
| GET | `/api/task/douyin/status?serial=` | — | 返回 phase/进度/最近事件，复用 `monitor.snapshot()` |

> 若评审认为不必新增路由：桌面端可直接用现有 `POST /api/task` 提交抖音 `TaskScript`，零后端改动，仅加桌面 UI。**推荐先走这条**（见 §6 阶段一）。

### 4.7 桌面客户端扩展

在 `win_console/app.py` 现有分组旁新增「任务」面板（抖音 + 快手共用）：
- 设备选择（复用现有下拉框）
- 剧本选择/编辑（加载 `tasks/douyin.json` / `tasks/kuaishou_checkin.json`）
- 「开始」「停止」按钮 → `POST /api/task` / `POST /api/device/<s>/stop`
- 进度/日志显示 → 轮询 `/api/status` 或复用 `log_signal`
- 校准按钮（可选）→ 触发截图 + 区域标注

### 4.8 快手极速版打卡任务方案（新增）

#### 4.8.1 包名与入口

| 版本 | 包名（待设备实测确认） | 说明 |
|---|---|---|
| 快手极速版 | `com.kuaishou.nebula` | 打卡任务主体目标 |
| 快手主版 | `com.smile.gifmaker` | 如需覆盖主版，同一套剧本换 `package` 即可 |

> 与抖音一致：`package` 写在剧本里，由 `adb.openApp(package)` 启动，不写死 Activity。

#### 4.8.2 任务链路与现有 phase 映射

快手极速版打卡与抖音的"循环上滑"不同，是**一次性定点任务**：

```
打开 App
  → 进入任务中心（用 loop.nav[] 点击"任务/赚钱"入口，tomato_novel.json 已有先例）
  → 定位打卡入口（checkIn.entryRegion / entryKeywords，如"每日打卡""签到"）
  → 点击打卡（reward.button 语义）
  → [若弹激励视频] 走 videoAd：等待 → 领取 → 校验
  → 校验金币数值 / 连续天数（RewardVerifier.verify）
  → 写入 monitor.progress.lastCheckIn = 今日日期（幂等）
```

状态机新增 2 个 phase（在 `lib/models.dart` 的 `TaskPhase` 追加）：
- `checkIn`：定位并点击打卡入口
- `claiming`：点击"领取"并等待结果

其余 `opening / nav / videoAd / verifying` 全部复用现有实现。

#### 4.8.3 幂等与定时（打卡特有，必须做）

| 问题 | 方案 |
|---|---|
| 重复打卡 | `monitor.progress` 增加 `lastCheckIn`（`YYYY-MM-DD`，按 serial 隔离）；任务启动时若今日已打卡则直接跳过 |
| 跨天执行 | 现有无 cron；用客户端/定时器每天触发一次任务提交，由幂等键保证一天只生效一次 |
| 打卡失败 | 不写 `lastCheckIn`，下次重试；失败原因记入 `monitor.events` |
| 连续天数中断 | 校验 `verifyRegion` 的"连续 N 天"文案，与上次记录比对，异常则告警不重试（避免误点导致断签） |

> 幂等逻辑放在 `Scheduler` 任务入口处，与 App 无关；抖音剧本不启用 `checkIn` 段时不受影响。

#### 4.8.4 识别与校准

复用 `detector.dart` 三策略，打卡场景建议组合：

| 目标 | 推荐策略 | 配置字段 |
|---|---|---|
| 任务中心入口 | region 或 ocr | `nav[].region` / `nav[].keywords` |
| 打卡按钮 | template（图标稳定）或 ocr | `checkIn.entryRegion` / `entryKeywords` |
| 领取按钮 | region / ocr | `videoAd.claimRegion` / `claimKeywords` |
| 金币 & 连续天数 | ocr（需 tesseract chi_sim） | `verifyRegion` / `successKeywords`（含"金币""连续"） |

需按机型校准的归一化区域（同 §4.5）：任务中心入口、打卡按钮、领取按钮、金币/连续天数显示区。建议复用 `coin_watch.py --calibrate` 的输出格式。

#### 4.8.5 客户端与接口

- 桌面「任务」面板增加剧本下拉项 `快手极速版-每日打卡`
- 复用 `POST /api/task` 提交；如需独立路由则加 `POST /api/task/kuaishou`（同 §4.6）
- 打卡结果（成功/已跳过/失败）在面板显示，并标注今日日期

#### 4.8.6 真机实测与已实现脚本（2026-11-21，EBG-AN00）

**目标澄清**：用户要的是「去赚钱 → 任务中心 → 日常任务」里的「**连续打卡白拿新手机**」卡片，
点它的「去领取」会打开「**完成365天打卡任务 白拿好礼**」WebView 页。
这与「连续看视频7天 0.76元」红包卡片是**两个不同任务**，不要混淆。实测机制：

- 导航链路：快手首页 → 底部「去赚钱」→ 任务中心 → 「连续打卡白拿新手机」的「去领取」→ 365天打卡 WebView
- 页面显示「已坚持 27 天」「今日打卡任务 5/6」；6 项任务中唯一未完成的是「观看广告 (N/20)」
- 点「去观看」→ 弹窗提供两条路：① 免费「观看N个广告完成任务」；② **消耗金币跳过（快速通道）**，金额随剩余数递减（实测 15300→7200）
- **决策：只走免费路径，绝不支付金币**
- 任务中心会反复弹「翻倍任务开启」干扰弹窗，脚本自动识别并关闭（坐标 `(0.90,0.20)` 的 ×）

已实现 `tools/ks_quick_checkin.py`（纯免费看广告，无任何支付逻辑）：
- **动态定位卡片（关键）**：任务中心里该卡片位置每天变化（完成/优先级变化会移动）。
  用 `cv2.matchTemplate`（`TM_CCOEFF_NORMED`，多尺度 `img.width/540` 归一）匹配
  `templates/ks_checkin_row.png` 整行卡片，逐屏上下滚动查找；实测命中 score 0.975，
  打卡页误报 score 0.284（阈值 0.70），**找不到就 exit 5 且零点击**，绝不误进其它任务页。
  按钮坐标由模板位置+偏移推算（`tw*0.88, th*0.15`），不是写死坐标。
- 自动导航：前台校验 → 若已在打卡页/弹窗则复用，否则 `am start HomeActivity` → 点「去赚钱」→ 关翻倍弹窗 → 滚动找卡片 → 点「去领取」→ 轮询等 WebView 加载 → 打卡页
- 看广告循环：点「去观看」→ 弹窗二选一，**只点上方免费项「观看N个广告完成任务」** →
  校验绿勾已选/红勾已取消才点底部动作按钮（任一确认失败立即零点击退出，绝不点「消耗金币/去支付」）→
  等够时长 → 遇「再看N秒领取奖励」点「继续观看」→ BACK 回打卡页 → 广告计数 +1
- 6/6 完成后弹「打卡成功 看完广告领取惊喜奖励」→「立即领取」→ 看完最后一条奖励广告 → 关闭
- 安全闸门：前台不是 `com.kuaishou.nebula` → exit 3 且零点击（实测前台为华为天气时正确拒绝）
- 幂等：`.tools/ks_checkin_state.json`（同日同 serial 跳过，未确认成功则记为可重试）；每步截图存 `.tools/ks_shots/`
- 参数：`--rounds`（最多几条广告）、`--delay-min/--delay-max`（广告间随机延时，默认 8~20s）、`--force`（忽略幂等）、`--dry-run`（不写幂等记录）

- 免费项校验：二选一弹窗默认免费项选中（红勾），用 `find_red_check()` 全屏找红色圆勾（area>700，中心如 `(865,1487)`），校验其 y 在选项区上半（<0.69h）才点「去完成」；付费项选中则拒绝点击。绝不点消耗金币。
- **视频**：定位按钮 `(910,974)` → 倒计时 `79:20→79:11→79:01` 递减，`progressed=True` ✓
- **短剧**：定位按钮 `(910,1313)` → 倒计时 `29:29→29:20→29:10` 递减 ✓
- **签到**：今日已完成时行变灰「已完成」、模板定位不到 → 正确返回"已完成"（幂等依据）。
- **热门内容**：定位按钮 `(910,2178)` → 免费项确认进入 → 看 25 秒 → 连续返回打卡页回读 `(N/5)` / 按钮完成态。
- **下载并体验随机 APP**：无中文 OCR、`uiautomator dump` 因动画失败 → 无法可靠识别每天随机的目标 APP，按约束**保守跳过**（截图留档目标行，绝不点去下载/误装）。待评审接入中文 OCR 或落地页识别后再启用。

**关键设计决策（2026-11-22 修订：一次运行持续做到完成）**：
1. **修复"每次只执行一次就退出"**：原实现看固定 90 秒 / 热门看 25 秒就退出，远未完成 80/30 分钟和 5 次。现改为——
   - 时长型（video/drama）：一次运行内**循环上滑观看直到 App 倒计时归零 `00:00`，再回打卡页确认该行完成**才算 `ok=True`；默认超时上限 video=5400s(90分)/drama=2400s(40分)，足够一次做完。
   - 热门内容：一次运行内**循环进入观看到计数满 `(5/5)` 或按钮变灰完成**（最多 40 轮），不再看一次就退。
2. **倒计时任务级持久（真机对照验证）**：短剧 `ENTER1=26:58 → 看30秒 26:27 → 退出重进 ENTER2=26:28`（延续未重置）。故中途被弹窗/作者页/落地页打断时，`_ensure_checkin()` 自动回打卡页并重进内容页继续，进度不丢。超时未归零记 `in_progress`，`--force` 下次运行继续累积；不做本地计时估算。幂等仅 `ok=True` 才跳过。
3. **全面改用 OCR 定位（2026-11-22 用户要求，解决"无法进入广告/点错窗口"）**：
   - 根因：打卡项完成数变化会让任务行上下移动（如广告行按钮从硬编码 `y=970` 实际移到 `y=1144`），硬编码坐标点空；底部「去赚钱」是艺术字被 OCR 读成乱码但坐标 `(758,2274)` 有效，彩色判定 `is_checkin_page/is_earn_page` 在任务展开后失效。
   - 落地：`ks_ocr.py` 用 RapidOCR 识别屏幕文字——按钮（`find_row_button('观看广告','去观看')`）、弹窗标题（「今日广告任务/翻倍任务开启」用文字判定替代颜色，消除误报循环）、计数（`read_count_near` 读 `(0/20)`）、页面判定（`is_checkin_page` 认「完成365天打卡任务」标题、`is_earn_page` 认「金币+日常任务」）。× 关闭按钮 OCR 优先、坐标回退。
   - 领奖后横幅 × 是图标 OCR 认成乱码且坐标波动 `(317~494,228)`，改为先 `back` 再由 `_ensure_checkin` 接管回打卡页。
4. **看广告并入 365 打卡（2026-11-22）**：`--task ad` 全链路 OCR——OCR 定位广告行按钮 → 二选一弹窗校验红勾在免费项（拒绝「消耗18000金币/跳过今日任务」）→ OCR 点「去看广告」→ 等「已成功领取奖励」（排除广告中「Ns后可领取奖励」倒计时误判）→ 回打卡页回读 `(N/20)` 循环看满 20 条。真机验证计数从 `0/20` 递增到 `10/20`，入口不再卡首页视频流（修复了误点 `(504,2274)` 点空的问题，正确为 `758,2274`）。原 `ks_quick_checkin.py` 保留作独立旧入口参考。
5. 数字识别用 IoU 而非 NMS，避免中文"时"字/括号误匹配；宽度过滤 `w>=h*0.42` 排除括号斜杠；解析规则"首位=当前、末段=总数(5/20/10/6)"。
6. 行定位用整行图像指纹（比单图标/单字模板稳），滚动时逐屏匹配。

**待评审**：仅「下载并体验随机 APP」处于保守跳过态（每天随机且无可靠 OCR 目标名）；其余 5 项（签到/视频/短剧/热门/广告）已整合进 365 打卡脚本并用 OCR 定位。

## 6. 分阶段实施计划（评审后可选）

| 阶段 | 内容 | 产出 | 依赖 | 估算 |
|---|---|---|---|---|
| 一 | 零后端改动：写 `tasks/douyin.json`，用现有 `/api/task` + Web 控制台跑通"打开→上滑→停止" | 可用剧本 1 份 | 无 | 0.5~1 天 |
| 二 | 把 `coin_watch.py` 的 ROI 差分移植为 `detector.dart` 的 `DiffRewardDetector`，接入 `Scheduler` | 看视频+金币增长检测 | 阶段一 | 1~2 天 |
| 三 | 补广告识别与 `videoAd` 领取校验（复用 `detector`/`RewardVerifier`），按机型校准 | 完整链路 | 阶段二 | 2~3 天 |
| 四 | 桌面客户端加「任务」面板与进度展示（抖音+快手共用） | 客户端可用 | 阶段一~三 | 1~2 天 |
| 五 | 多设备并行、异常恢复与报告 | 稳定版 | 阶段四 | 2~3 天 |
| 六 | **快手极速版打卡**：`CheckInConfig` + `checkIn`/`claiming` phase + 幂等键 + `tasks/kuaishou_checkin.json` + 客户端选项 | 打卡可用 | 阶段一、四（可独立先做） | 2~3 天 |

> 阶段六可与阶段一并行：打卡不依赖 ROI 差分（`DiffRewardDetector`），只依赖 nav/click/校验，可与抖音看视频独立决策。

**MVP 建议**：
- 抖音线：只做阶段一+二，先验证"看视频+金币检测"稳定性；广告与领取是否继续由评审按合规结论决定。
- 快手线：只做阶段六，先验证"每日打卡 + 幂等"正确性；激励视频环节按合规结论决定。

## 7. 测试与验收

- **单元**：`detector` 三策略对样本截图的识别率；`RewardVerifier` 对领取前后帧的判定；`Scheduler` 幂等键对同日重复提交的跳过
- **集成（抖音）**：单设备跑 N 轮，统计：卡死次数、误触次数、金币增长检出次数、任务完成率
- **集成（快手）**：同日连续提交 2 次，验证第 2 次被跳过；隔日提交验证可执行；打卡失败不写 `lastCheckIn`
- **兼容**：至少 2 种机型/分辨率（坐标归一化验证）
- **人工兜底**：随时可点「停止」；异常时 `monitor.events` 有记录；`recover()` 能回到 App 首页
- **验收线**：抖音连续 1 小时无人工干预、无误触外泄；快手打卡 7 天连续天数不断、幂等 100% 生效；两者状态可观测

## 8. 风险登记册（评审重点）

| ID | 风险 | 缓解 |
|---|---|---|
| R1 | 账号封禁/收益清零 | 仅自用/小号；不规模化；随时停止 |
| R2 | 平台 UI 改版导致区域失效 | 坐标归一化 + 多策略识别 + 剧本可改不需改代码 |
| R3 | OCR 依赖外部 tesseract | 优先用 region/template；OCR 作为可选 |
| R4 | 多设备性能下降 | 限制并发数；每设备独立 scrcpy 进程（现状已如此） |
| R5 | 鸿蒙设备 hdc 通道差异 | 复用 `LinkRouter`；截图走 `/frame/<s>` 轮询 |
| R6 | 合规争议 | **评审阶段决定做不做**，技术侧不预设结论 |
| R7 | 快手打卡误点导致连续天数中断 | 幂等键 + 校验"连续 N 天"文案；异常只告警不自动重试，交人工复核 |
| R8 | 快手任务中心 UI 改版 | 三策略识别 + 剧本可改不需改代码；入口 region/keywords 双保险 |

## 9. 结论与待决策项

**技术结论**：现有架构已覆盖"投屏→控制→识别→调度→校验→监控"全链路。
- 抖音场景：**新增一份剧本 + 移植一个检测器 + 加一个客户端面板**，不需要重构，约 5~10 人天（视阶段）。
- 快手打卡：与抖音共用引擎，仅新增 `CheckInConfig`、2 个 phase、幂等键与一份剧本，**约 2~3 人天**，可独立于抖音线先做。

**请评审决策**：
1. 是否实施？抖音线与快手线可分别决策（建议 MVP：抖音=阶段一+二，快手=阶段六）。
2. 账号/设备范围？（自用 / 小号 / 多设备）
3. 广告与金币领取是否纳入？（合规风险最高）
4. 快手打卡是否要求"连续天数"强校验？异常时仅告警还是暂停后续任务？
5. 是否需要桌面客户端 UI，还是 Web 控制台够用？
