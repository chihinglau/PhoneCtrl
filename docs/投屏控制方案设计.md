# PhoneCtrl — PC 端投屏与手机自动化控制方案

> 本方案复刻参考项目 `MyGameSim`（趣玩匣 GamePouch）的 PC 端工程结构：
> **PowerShell 脚本层 + Dart 零依赖服务层 + ADB 封装层 + Web 监控台**，
> 并将其从「ROM 同步」场景迁移到「投屏 + 自动化操作」场景：
> 通过 ADB 控制手机自动打开指定 App、执行滑屏、点击广告、领取奖励。
>
> 在此基础上新增 **Windows 桌面控制台（PyQt5 + Win32 原生窗口嵌入）**，
> 把 scrcpy 的流畅投屏与设备控制台整合进同一个桌面窗口，支持**多设备同时投屏、画面按比例均匀分配**。

版本：v0.2.0 · 目标平台：Android（AOSP 兼容层 / HarmonyOS 4.x 兼容 adb）· 语言：Dart 3 + Python 3.10 + PowerShell 5.1

## 1. PC 端投屏与控制架构

### 1.1 总体分层（对齐参考项目）

```
PhoneCtrl/
├── scripts/                 # ① 脚本层：环境注入、启动/停止、健康检查（对齐 MyGameSim/scripts）
│   ├── setup-env.ps1        #   拉取/钉版 adb、scrcpy 工具链（复用 .tools 目录约定）
│   ├── use-env.ps1          #   注入 ANDROID_HOME / PATH（每个新终端先执行）
│   └── phone-ctrl.ps1       #   一键启动 PC 控制器（端口占用保护 + adb 设备预检）
├── run_server.ps1           #   启动 Dart 服务（桌面控制台未检测到后端时自动拉起）
├── tools/control/           # ② Dart 零依赖服务层（对齐 MyGameSim/tools/library）
│   ├── server.dart          #   入口：HTTP 监控台 + 控制台 + 任务调度总线 + 设备控制 API
│   ├── lib/

│   │   ├── device.dart      #   设备发现 / 状态（Device 类）
│   │   ├── screen.dart      #   投屏（scrcpy 外挂）+ 截图采集
│   │   ├── automation.dart  #   手机端自动化操作（openApp/swipe/tap/wait）
│   │   ├── detector.dart    #   广告识别 + 奖励校验策略（策略模式）
│   │   ├── scheduler.dart   #   任务调度（DeviceTask 队列 + 并发）
│   │   ├── monitor.dart     #   状态监控（指标采集 + 事件总线）
│   │   ├── config.dart      #   任务剧本（JSON 驱动，可复用不同 App）
│   │   ├── models.dart      #   公共数据模型（RPoint / OpResult 等）
│   │   └── swipe.dart       #   自动滑屏方向/坐标解析
│   └── web/                 #   ③ Web 监控台（原生 HTML/JS，对齐 lib/web）
│       └── index.html       #   实时投屏画面 + 设备状态 + 任务进度
├── win_console/             # ④ Windows 桌面控制台（PyQt5，零额外依赖）
│   └── app.py               #   scrcpy 原生窗口嵌入 + 多设备网格 + 按键/解锁/自动滑屏
├── tasks/                   #   ⑤ 任务剧本（JSON）：每个 App 一套识别/坐标配置
│   └── sample_app.json
├── docs/                    #   方案设计文档
├── pubspec.yaml
└── README.md
```

### 1.2 三大平面

| 平面 | 职责 | 参考项目对应 |
|------|------|--------------|
| **投屏平面** | 用 `scrcpy` 将手机画面低延迟投射到 PC 窗口，便于人工观察与调试；用 `adb exec-out screencap -p` 抓帧供自动化分析 | 参考项目无（新增平面） |
| **控制平面** | `Adb` 封装类统一下发 `shell`（input tap/swipe、am start、dumpsys）指令，带重试与超时 | 参考项目 `Adb` / `SyncEngine` |
| **决策平面** | `detector` 对截图做广告/奖励识别，`scheduler` 编排任务，`monitor` 汇总状态并通过 HTTP 暴露 | 参考项目 `Store` / `SyncJob` |

> 复用要点：PC 端一律用 `dart:io` 零依赖（不引入第三方包），外部二进制（adb/scrcpy）
> 通过 `ANDROID_HOME` / `PATH` 解析，与参考项目 `Adb.exe` 解析逻辑一致。

### 1.3 投屏方案选型

- **实时投屏**：`scrcpy`（开源，依赖 adb），由 `screen.dart` 负责启动/停止，断线自动重连。
- **采集帧（给自动化看）**：不依赖 scrcpy，单独走 `adb exec-out screencap -p > frame.png`，
  避免占用 scrcpy 的视频流，二者解耦。
- **坐标体系**：以手机物理分辨率（通过 `wm size` 获取）为基准，所有坐标在 JSON 剧本中以
  相对比例（0.0~1.0）描述，运行时乘以当前分辨率，自动适配不同机型/横竖屏。

## 2. ADB 指令封装与手机端自动化操作模块

### 2.1 `Adb` 封装类（继承参考项目范式）

对齐 `MyGameSim/tools/library/server.dart` 中的 `Adb`：

- `exe`：优先 `ANDROID_HOME/platform-tools/adb.exe`，否则回退 `adb` 全局命令（与参考一致）。
- `run(args)`：底层 `Process.run`，统一编码（`systemEncoding`）。
- `shell(serial, cmd)`：`-s <serial> shell ...`，非零退出抛异常。
- `devices()`：解析 `adb devices -l`，返回 `Device` 列表（含 serial / state / model）。
- `tap / swipe / keyEvent / startActivity / screenshot / currentApp`：业务语义方法。
- `waitFor(predicate, timeout)`：轮询封装，供上层等待条件。

```dart
// 与参考项目一致的 exe 解析
String get exe {
  final home = Platform.environment['ANDROID_HOME'];
  if (home != null) {
    final p = File('$home/platform-tools/adb.exe');
    if (p.existsSync()) return p.path;
  }
  return 'adb';
}
```

### 2.2 手机端自动化操作模块（`automation.dart`）

围绕「打开 App → 滑屏 → 点击 → 等待」封装原子操作，全部带重试：

| 操作 | ADB 指令 | 说明 |
|------|----------|------|
| `openApp(pkg, [activity])` | `am start -n pkg/activity` 或 `monkey -p pkg 1` | 启动指定 App；未在前台时强制拉起 |
| `tap(rx, ry)` | `input tap x y` | 按比例坐标点击 |
| `swipe(rx1,ry1,rx2,ry2,ms)` | `input swipe x1 y1 x2 y2 ms` | 滑屏（上下翻页/切广告） |
| `keyEvent(code)` | `input keyevent KEYCODE_BACK` 等 | 返回键、Home 等 |
| `waitApp(pkg, timeout)` | `dumpsys window | grep mCurrentFocus` | 等待目标 App 进入前台 |
| `waitStable(timeout)` | 连续两帧灰度差值 < 阈值 | 等待画面静止，避免误判 |
| `screenshot()` | `screencap -p` | 返回 PNG 字节 |

所有原子操作返回 `OpResult{ok, attempt, costMs, detail}`，供调度层做重试决策。

## 3. 广告识别与点击策略

识别策略采用**策略模式**（`AdDetector` 接口），可针对同一画面叠加多种检测器，命中其一即执行点击。

### 3.1 三种内置策略

1. **区域坐标策略 `RegionAdDetector`**（最稳，默认）
   - 剧本中以相对坐标框 + 颜色特征描述「广告位」（如右下角 banner、信息流卡片）。
   - 运行时裁剪该区域，比对预设主色/模板，命中即点中心。
2. **模板匹配策略 `TemplateAdDetector`**
   - 预先截取「点击广告 / 查看详情 / 立即下载」按钮模板（PNG），运行时用
     归一化互相关（NCC）/ 像素差值在候选区域内滑动匹配。
3. **文本/OCR 策略 `OcrAdDetector`**（可选）
   - 预留 `OcrProvider` 接口，可挂接本地 `tesseract` 或云端 OCR；
     命中关键词（广告、领、立即、下载）即点。

### 3.2 误点防护

- 点击前校验**不在误触区**（如系统状态栏、返回键、支付确认框坐标白名单）。
- 点击后 `waitStable` + `waitApp` 校验：若意外跳转到应用商店/浏览器且非预期，
  立即 `keyEvent(BACK)` 回退并记录一次失败。
- 单轮「广告点击」有次数上限（`maxAdClicks`），防止进入死循环。

## 4. 奖励领取的触发与校验机制

### 4.1 触发

- **显性触发**：广告播放完/落地页出现「领取奖励 / 领取金币 / 立即领取」按钮
  （由 `RewardDetector` 识别，复用 `AdDetector` 策略栈）。
- **隐性触发**：等待固定时长后轮询奖励弹窗区域，超时未出现则标记该轮无奖励。

### 4.2 校验（关键，防止「假领取」）

采用「**领取前快照 → 领取动作 → 领取后校验**」三段式：

1. **数值校验**（优先）：剧本标注金币/积分显示区域；领取前抓帧 OCR/模板读值 `v0`，
   领取后读 `v1`，当且仅当 `v1 > v0` 判定成功。
2. **UI 状态校验**（兜底）：检测「领取成功 / +100 / 已领取」Toast 或按钮变为
   「已领取/置灰」状态。
3. **副作用校验**（兜底）：`dumpsys` 检测新增通知 / 文件落盘（部分 App 领奖写本地）。

校验失败时：记录 `RewardResult{missed}`，按重试策略再走一轮广告。

## 5. 异常处理与操作重试逻辑

### 5.1 异常分类

| 类型 | 示例 | 处理 |
|------|------|------|
| 设备异常 | 离线 / 未授权 / 黑屏 | 暂停该设备任务，monitor 告警，恢复后自动续跑 |
| 指令异常 | `input tap` 超时、shell 非零退出 | 立即重试（幂等操作） |
| 识别异常 | 截图全黑 / 找不到广告 / 奖励未校验 | 重试当前阶段，超限则跳过该轮 |
| 逻辑异常 | 跳错页面 / 误触支付 | `keyEvent(BACK)` 回退 + 重置 App 到首页再重试 |

### 5.2 `RetryPolicy`（对齐参考项目 `SyncJob` 的失败计数范式）

```dart
class RetryPolicy {
  final int maxAttempts;     // 最大尝试次数
  final Duration base;       // 基础退避
  final double factor;       // 指数因子
  final bool Function(Object e) retryable; // 是否可重试
}
```

- 指数退避 + 抖动（避免多设备同时重连冲击）。
- 每阶段独立计数；单设备单任务总失败次数超过 `maxTaskFails` 进入 `failed` 终态并告警。
- 所有操作幂等化：tap/swipe 天然幂等；openApp 重复调用安全；奖励领取靠第 4 节校验去重。

## 6. 整体任务调度与状态监控

### 6.1 任务模型（JSON 驱动，可复用）

`tasks/<app>.json` 描述一套完整剧本，便于适配不同 App：

```jsonc
{
  "appName": "示例激励 App",
  "package": "com.example.reward",
  "home": { "tap": [0.5, 0.9] },          // 回首页锚点
  "loop": {
    "rounds": 20,                          // 总轮数
    "openApp": true,
    "swipe": { "from":[0.5,0.8], "to":[0.5,0.2], "ms":400, "times":3 },
    "ad":   { "region":[0.05,0.55,0.95,0.95], "strategy":"region|template", "maxClicks":2 },
    "reward": { "button":[0.5,0.85], "verifyRegion":[0.4,0.1,0.6,0.2], "timeoutMs":8000 },
    "backHome": true
  }
}
```

### 6.2 调度器 `Scheduler`

- 每设备一条 `DeviceTask` 流水线；多设备可并发（各自独立 serial）。
- 阶段状态机：`idle → opening → swiping → adClicking → rewarding → verifying → done/failed`。
- 支持「单轮 / 连续 N 轮 / 定时循环（cron-like 间隔）」。
- 断点续跑：每轮结束持久化进度到 `.tools/phonectrl.state.json`。

### 6.3 监控 `Monitor` + Web 控制台

- 采集：设备在线/电量/`currentActivity`、当前阶段、本轮次、成功/失败计数、最近截图。
- HTTP 接口（端口 8858，对齐参考 8848）：
  - `GET  /`            Web 监控台（投屏缩略图 + 状态）
  - `GET  /api/status`  全设备 JSON 状态
  - `POST /api/task`    提交/启动任务剧本
  - `POST /api/device/:s/stop` 停止某设备
- 控制台实时刷新：阶段进度条、成功/失败率、最近一帧截图，便于人工介入。

## 9. Windows 桌面控制台（PyQt5 + Win32 原生窗口嵌入）

Web 控制台解决了"状态与任务管理"，但投屏体验依赖浏览器插件/MJPEG 转码（延迟高、CPU 占用大）。
第 9 章描述本方案新增的**桌面端**：把 scrcpy 的**原生渲染窗口直接嵌入** Qt 界面，
一个窗口同时承载"流畅投屏 + 设备控制"，支持多设备同时投屏。

### 9.1 总体架构

```
PhoneCtrl 桌面控制台（win_console/app.py，PyQt5）
┌──────────────────────────────────────────────────────────────┐
│ 左侧：video_area（唯一 native 容器）                            │
│   ┌─────────────┐  ┌─────────────┐  ┌─────────────┐          │
│   │ cell #1     │  │ cell #2     │  │ cell #3     │  ← 手动 │
│   │ tag(序列号) │  │ tag(序列号) │  │ tag(序列号) │   几何分配│
│   │ host(QFrame)│  │ host(QFrame)│  │ host(QFrame)│          │
│   │  └ scrcpy①  │  │  └ scrcpy②  │  │  └ scrcpy③  │  ← Win32 │
│   └─────────────┘  └─────────────┘  └─────────────┘   子窗口  │
├──────────────────────────────────────────────────────────────┤
│ 右侧：设备下拉 / 启动·全部·停止投屏 / Home·返回·任务·电源        │
│       一键解锁（PIN）/ 自动滑屏开关 / 日志                      │
└──────────────────────────────────────────────────────────────┘
        │ HTTP（urllib，零依赖）
        ▼
Dart 服务（tools/control/server.dart，端口 8858）—— 复用现有 REST API，一行不改
```

**职责边界**：Python 只做"窗口嵌入 + 界面 + 调用 REST API"；所有设备操作仍走 Dart 服务层
（`Adb` 封装、调度、状态监控全部复用）。Python 侧新增的唯一后端能力是
`POST /api/device/<serial>/unlock`（见 9.5）。

### 9.2 scrcpy 窗口嵌入机制（Win32 ctypes）

不引入 `pywin32`，直接用 `ctypes` 调 `user32`：

1. 每台设备启动一个独立 scrcpy 进程，用 `--window-title PhoneCtrl-<serial>` 保证窗口可被
   `FindWindowW` 精确找到（多设备标题唯一）；
2. `SetWindowLongW` 把 scrcpy 窗口样式从 `WS_POPUP` 改为 `WS_CHILD | WS_CLIPSIBLINGS`
   （后者保证多设备窗口互不越界绘制）；
3. `SetParent` 挂到 `video_area` 的 native HWND（`QWidget.winId()`，容器加 `WA_NativeWindow`）；
4. `SetWindowPos` 把子窗口钉到目标矩形。

启动参数：`--window-borderless --window-width W --window-height H --max-fps 60 --no-audio`，
其中 W/H 取该设备分配到的格子尺寸（物理像素），避免启动瞬间闪烁。

> **为什么不把 scrcpy 窗口嵌到每个格子的 QFrame 上？**
> 早期方案为每个格子创建 native 宿主窗口（`host.winId()` + `WA_NativeWindow`），
> 但发现 **Qt 对 native 子窗口的几何同步不可靠**：窗口在布局未定型时创建后，
> 后续布局变化不会同步到该 native 窗口，导致其客户区尺寸仍是旧值（表现为"全屏宽"、覆盖其他格子）。
> 最终方案：**所有 scrcpy 窗口统一挂在唯一 native 容器 `video_area` 下，
> 位置与尺寸全部由 Python 用 Qt 布局数据计算后显式 `SetWindowPos`**，
> 不依赖任何 native 窗口自身的几何状态，从机制上消除该问题。

### 9.3 多设备画面分配算法

`_apply_geometry()` 按**手机竖屏比例**分配，而不是简单 `ceil(√N)` 网格（那样单设备时格子过宽、
画面被 letterbox 缩小）：

1. 目标格子宽高比 `aspect ≈ 0.5`（9:18 竖屏近似）；
2. 枚举列数 `cols = 1..N`，取「每格面积最大」的方案（并列时取列数更小者，布局更整齐）；
3. 每格在其槽位内**居中**，槽位尺寸 = 可用区 / (cols × rows)；
4. 每台设备 scrcpy 窗口 = 对应格子的矩形（Qt 逻辑坐标 × `devicePixelRatioF()` = 物理像素）。

效果：1 台居中手机形；2 台左右各一；3 台一行三个；4 台 2×2……窗口缩放时 `resizeEvent`
与每秒定时器都会重算并重新摆位（自愈，1 秒内收敛）。

### 9.4 关键实现要点与踩坑记录

| # | 问题 | 根因 | 解法 |
|---|------|------|------|
| 1 | 投屏窗口很小，只占左上角 | Qt 返回**逻辑像素**，`SetWindowPos` 需要**物理像素**，高 DPI 屏（125%/150%/200%）下尺寸被系统缩小 | 所有尺寸乘 `devicePixelRatioF()` |
| 2 | 单机画面小、双机互相覆盖 | native 宿主窗口几何未随布局更新（见 9.2） | 改为唯一 native 容器 + Python 显式算矩形摆位 |
| 3 | 多设备窗口重叠 | 子窗口无 `WS_CLIPSIBLINGS`，可绘制到兄弟窗口之上 | 嵌入时补 `WS_CHILD \| WS_CLIPSIBLINGS` |
| 4 | 「启动(选中)」弹"请先选择设备" | PyQt5 的 `clicked` 信号会把 `checked=False` 作为首参传给槽函数，`serial=False` 既非 None 又为假值 | 按钮统一 `connect(lambda: ...)` 屏蔽该参数 |
| 5 | 第二台 scrcpy 启动 3 秒后退出 | 多实例同时启动抢占资源；且 stderr 被丢弃无法定位 | 全部投屏时错开 1.5s 逐台启动；stderr 落盘到 `.tools/scrcpy_<serial>.log`，退出时自动附带错误尾部到日志面板 |

其他细节：

- **后端自动拉起**：启动时探测 `http://127.0.0.1:8858/api/status`，未就绪则自动
  `powershell -File run_server.ps1` 并轮询重试（最多 ~36s）。
- **scrcpy 进程管理**：`mirrors[serial] = {proc, title, hwnd, host, cell, tries}`；
  每秒轮询 `proc.poll()` 检测退出并自动清理对应格子。
- **线程安全**：所有 HTTP 调用放 `threading.Thread`（daemon），结果通过 `pyqtSignal` 回主线程刷 UI。
- **无显示器冒烟测试**：`QT_QPA_PLATFORM=offscreen` 下构造主窗口，验证 UI 装配不崩
  （CI / 无 RDP 环境可用）。

### 9.5 新增后端接口：一键解锁

按电源键锁屏后，一键完成「唤醒 → 上滑 → 输入 PIN」：

```
POST /api/device/<serial>/unlock
Body: { "password": "1234", "swipeUp": true }
```

服务端流程（`server.dart` 的 `_deviceUnlock`）：

1. `input keyevent 224`（`KEYCODE_WAKEUP`，亮屏时不会像 `KEYCODE_POWER` 反而熄屏）；
2. `swipeUp` 为真时按相对坐标 `(0.5,0.82)→(0.5,0.16)` 上滑露出密码键盘；
3. 逐位输入 PIN：数字字符 `'0'-'9'` 映射为 `KEYCODE_0=7 … KEYCODE_9=16`，
   每位间隔 120ms；PIN 锁满位后自动校验。

限制：仅支持数字 PIN；图案锁/字母密码未覆盖；少数机型锁屏键盘只认触摸点击，
需要坐标点按版兜底（后续可扩展）。
